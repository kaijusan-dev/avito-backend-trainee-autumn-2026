
# CJM - Со стороны заведения

## Цель

Показать, как заведение взаимодействует с Avito.Kitchen: управляет товарами, получает заказы и изменяет их статусы.

## Участник

**Сотрудник заведения** - человек, который отвечает за актуальность меню и обработку заказов.

В рамках проекта взаимодействие с системой представлено через Restaurant API. Отдельный интерфейс сотрудника не реализуется.

## Основной сценарий

### 1. Управление заведением

Restaurant API предоставляет информацию о заведении.

Сервис хранит данные заведения в собственной базе данных.

### 2. Управление товарами

Сотрудник может получать информацию о товарах и изменять их данные.

В частности, можно:

- изменять название товара;
- изменять стоимость;
- изменять доступность товара.

Изменения сохраняются в Restaurant PostgreSQL.

**Результат:** информация о товарах остаётся актуальной.

### 3. Получение нового заказа

Когда клиент оформляет заказ:

1. Platform API проверяет товары через Restaurant API.
2. Platform API передаёт подтверждённый заказ в Restaurant API.
3. Restaurant API проверяет полученные данные и сохраняет заказ в собственной базе данных.

Заказ получает тот же идентификатор, который был создан на стороне Platform API.

**Результат:** заказ появляется в системе заведения.

### 4. Просмотр заказов

Сотрудник может получить:

- список заказов;
- список заказов с фильтрацией по статусу;
- информацию об отдельном заказе.

Данные для этих запросов Restaurant API получает из собственной базы данных.

### 5. Обработка заказа

По мере выполнения заказа сотрудник изменяет его статус.

Restaurant API проверяет возможность изменения статуса и сохраняет новое значение в Restaurant PostgreSQL.

Завершённые и отклонённые заказы больше нельзя изменять.

**Результат:** в системе заведения хранится актуальный статус заказа.

### 6. Передача статуса клиенту

Когда клиент запрашивает информацию о заказе:

- Platform API получает основные данные заказа из своей базы данных.
- Platform API обращается к Restaurant API за актуальным статусом.
- Клиент получает обновлённый статус вместе с информацией о заказе.

Таким образом, Restaurant API отвечает за изменение статуса, а Platform API предоставляет клиенту информацию о заказе.

## Краткая схема сценария

1. Сотрудник -> Restaurant API: изменение товара.
2. Restaurant API -> Restaurant PostgreSQL: сохранение изменений.
3. Platform API -> Restaurant API: проверка товаров при оформлении заказа.
4. Platform API -> Restaurant API: передача нового заказа.
5. Restaurant API -> Restaurant PostgreSQL: сохранение заказа.
6. Сотрудник -> Restaurant API: просмотр заказов.
7. Сотрудник -> Restaurant API: изменение статуса заказа.
8. Restaurant API -> Restaurant PostgreSQL: сохранение нового статуса.
9. Клиент -> Platform API: запрос информации о заказе.
10. Platform API -> Restaurant API: получение актуального статуса.

## Возможные проблемы

- Товар не найден.
- Товар недоступен.
- Заказ не найден.
- Заказ уже завершён или отклонён.
- Переданные данные не прошли проверку.
